# 共同重构原则

本文只定义跨语言、跨 scope 都成立的重构要求。具体职责归属、依赖方向、生命周期和验证命令以对应的 [scope 文档](scopes/) 与 [language 文档](languages/) 为准。

## 判断依据

- 重构目标是提高内聚、明确 ownership、缩小变更影响面和提升可验证性，不是降低文件行数或扫描分数。
- “职责”必须能用稳定的业务、架构或生命周期概念命名。无法说明独立修改理由的代码，不应仅因体量或热点数量被拆出。
- 判断边界前必须阅读源码，并检查直接调用方、依赖、状态流、资源生命周期、测试和平台兼容路径。
- 扫描报告只能说明“这里值得检查”以及“哪些位置可能相关”，不能证明职责混杂。

## 合理边界

一次拆分至少应满足下列条件之一：

- 被拆出的内容具有独立且稳定的修改原因。
- 它拥有清晰输入输出、状态或资源 ownership。
- 它能够通过已有或新增的 focused test 独立验证。
- 它消除了不合理的依赖方向、重复实现或跨层规则泄漏。

拆分后，原 owner 与新 owner 的名称和职责都应更容易解释；调用链、依赖扇出或平台适配成本不应无理由上升。

## 禁止的指标驱动拆分

- 不按固定行数、函数数量或扫描阈值切文件。
- 不把同一资源的 create/poll/take/cancel/destroy 等生命周期机械拆散。
- 不为单个私有 helper、常量组或纯转发函数创建没有独立 owner 的微文件。
- 不通过复制实现、生成 fallback 副本或隐藏在 `.inc` 中来降低 owner 指标。
- 不为了让报告变绿而扩大公共 API、破坏既有依赖方向或引入循环依赖。

## 使用扫描证据

- `priority` 和 `score` 只用于安排阅读顺序。
- hotspot、cluster、move set 和 extraction candidate 只表示可能相关的代码区域。
- suggestion、next action 和 stop signal 是启发式假设，不是架构结论。
- baseline diff 用于发现意外碎片化、依赖扇出和复制实现，不能代替行为验证。

如果源码显示候选文件由一个清晰 owner 统一协调，即使它较大或仍有较高分数，也应保留现状并记录误报原因。

## 完成条件

重构完成前应确认：

1. 新旧 owner 的职责和不迁移内容均可明确描述。
2. 行为、契约、错误处理和资源释放语义保持正确。
3. focused validation、baseline 重扫以及所属 scope 的完整验证通过。
4. 没有新增无归属微文件、复制实现或异常依赖扇出。
